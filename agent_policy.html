Amazon BSA Agent Policy Compliance

ASINInsight satisfies the new Amazon Agent Policy by design, not by patch.

Amazon updated its Business Solutions Agreement on 2026-03-04 to add an Agent Policy for AI tools that act on a seller's behalf. Enforcement starts in early June 2026. This page documents how ASINInsight meets each requirement, with citations to our own code.

Last reviewed: 2026-05-09. Policy in effect: BSA updated 2026-03-04. Author: ASINInsight engineering.

What the policy requires

Three obligations for any AI agent that touches Amazon on a seller's behalf

The 2026-03-04 update introduces a defined category of "AI agents" and three explicit obligations. Coverage from PPC.land and EcommerceBytes summarizes the rules:

  1. AI agents must clearly identify themselves as automated systems at all times.
  2. AI agents must comply with the new Agent Policy at all times.
  3. AI agents must cease access immediately if Amazon requests it.

The same coverage explicitly notes: "Browser automation tools, those that control a browser to interact with Seller Central as if they were a human user, are the most directly targeted and are now explicitly prohibited regardless of what actions they perform."

Most existing PPC tools were not built around this policy. The 90-day grace window ends in early June 2026. Sellers using non-compliant tools risk having their connected apps revoked by Amazon.

How we satisfy each requirement

1. Self-identification on every Amazon API call

Implementation: ppc_ads_client.USER_AGENT constant.

Every outbound HTTP request from ASINInsight to an Amazon endpoint sends a User-Agent header that names the tool, declares it as an automated AI agent, and references the policy version it complies with:

ASINInsight/1.0 (Automated AI Agent;
  Amazon-BSA-Agent-Policy=2026-03-04-compliant;
  +https://asininsight.com/legal/agent-policy)

It is sent on every Amazon Ads API call (campaigns, ad groups, keywords, search-term reports) and every Login With Amazon OAuth token exchange. A continuous-integration test asserts that any code change which removes the policy markers from this header fails the build before the change can ship.

2. Architecture that complies by design

Implementation: data-access posture across the full codebase.

Policy concernASINInsight posture
Browser automationNot used. We never control a browser to interact with Seller Central.
ScrapingNot used. We use the official Sponsored Ads API and SP-API only.
Unauthorised data pipelinesNot used. Every byte of seller data comes from OAuth-authorised endpoints the seller explicitly connects to ASINInsight.
Unidentified automationMitigated by the User-Agent header above.
Unbounded data pullingMitigated by a 6-hour cache TTL plus per-app rate limits in our snapshot fetcher.

None of these are recent additions. The architecture has been OAuth-only and API-only since the first commit. We chose this posture before the BSA update was published.

3. Code-backed kill switch for cessation on Amazon's request

Implementation: ppc_agent._kill_switch_disconnect_all().

If Amazon asks us to cease access for a specific seller or for all sellers, we can do it in one call. The kill switch flips every active Amazon connection to inactive in a single transaction. Encrypted refresh tokens are preserved so the seller can reconnect later, but no further outbound API call happens until the seller takes that action.

Every kill-switch invocation appends a forensic record to our audit log: who triggered it, when, and how many connections were disconnected. We can produce that audit trail to Amazon on request.

Continuous-integration tests cover the refusal path when the admin token is unset, the refusal path on a bad token, the success path on a correct token, idempotency on a second call, and the invariant that refresh tokens are preserved through the disconnect.

Read-only safety mode

ASINInsight does not write to Amazon. Period.

This is a stronger posture than the policy requires, but it is the heart of how the product works. The policy is about how AI tools should behave when they act on a seller's behalf. ASINInsight answers a different question: "what if the AI does not act at all, and the seller does?"

Every recommendation our engine produces is queued in your dashboard with the math, the evidence, and a one-sentence reason you might still reject it. You read it. You decide. Nothing reaches Amazon until you click apply, and the apply path will require an explicit second confirmation when it ships.

A tool that cannot push changes cannot make a billing-surprise change, an account-suspending change, or a profit-destroying change. The structural answer to autopilot risk is to not be on autopilot.

What this page does not cover

Honest scope

This page covers the Amazon Ads and SP-API integration in our current MVP. It does not cover DSP or AMC compliance (we do not call those APIs yet), multi-marketplace data residency beyond the United States (architecture supports it but we have not certified it for EU or JP yet), or any future in-app browser-automation features (we explicitly do not build browser automation).

If your workflow needs any of these, write to support@asininsight.com and we will tell you whether and when we can support it. We will not pretend we already do.
